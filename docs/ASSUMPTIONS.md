# Assumptions and Design Decisions

This file records interpretations of the assignment and the policy document. It is updated as the
project progresses and summarized in the README.

## Money and rounding

- All amounts are stored as `NUMERIC(12,2)` and handled as `Decimal`; floating point is never used.
- Amounts are rounded to 2 decimal places using half-up rounding. Inputs with more than 2 decimals are rejected.
- A single currency per tuition record is stored (default `USD`, matching the policy document).

## Balance scope (term vs overall)

- Query Tuition returns the overall tuition total and balance for the student, plus a per-term breakdown.
- Pay Tuition is term-specific: `amount` must be positive and must not exceed that term's outstanding balance.
  Overpayments are not supported.

## Data model

- Terms are free-form strings validated against `YYYY-FALL`, `YYYY-SPRING` or `YYYY-SUMMER`.
- Each student has at most one tuition record per term (`UNIQUE (student_id, term)`).
- `tuitions.paid_amount` is a running total updated in the same transaction as each payment insert;
  `payments` is the immutable audit trail. See [er-diagram.md](er-diagram.md).

- The schema is created with SQLAlchemy `create_all` (`python -m app.seed`) instead of Alembic
  migrations, to keep the project simple. Integrity rules are enforced as database constraints.
- Passwords are hashed with PBKDF2-HMAC-SHA256 (600,000 iterations, random salt).

## Add Tuition duplicate handling

- Add Tuition is create-or-update keyed by `(studentNo, term)`: an existing record's amount and currency
  are replaced; otherwise a new record is created.
- If the student number does not exist yet, the student record is created automatically (admin is the
  system of record for tuition assessment).
- An update that would set `amount` below the already paid amount is rejected (`409 Conflict`).
- Changing the currency of a record that already has payments is rejected (`409 Conflict`).
- All tuition records of one student must use the same currency (`409 CURRENCY_MISMATCH`).
- A zero amount is allowed (e.g. full scholarship); negative amounts are rejected.
- The response is `201 CREATED` for a new record and `200 UPDATED` for an existing one.
- In a batch CSV, each row is processed independently; duplicate `(studentNo, term)` rows in the same
  file are applied in order (last one wins) and each is reported.
- Batch upload is `multipart/form-data` with a UTF-8 CSV file (BOM allowed, blank lines ignored, at most
  10,000 rows). A wrong header, an empty file or a non-UTF-8 file rejects the whole upload
  (`422 INVALID_CSV`). Otherwise the response is `200` with `status` `COMPLETED` (no errors), `PARTIAL`
  or `FAILED` (no row succeeded), counts, and per-row errors with the CSV line number.
- A sample file for the demo is in [samples/tuitions_batch_sample.csv](samples/tuitions_batch_sample.csv).

## Unpaid Tuition Status

- "Unpaid" means a tuition record with `balance > 0` (partially paid records are included).
- `term` is optional; without it all terms are listed. Results are ordered by student number, then term.
- Offset paging: `page` starts at 1, `pageSize` is 1-100 (default 20). A page past the end returns `200`
  with an empty `items` list; `totalItems` and `totalPages` are always returned.

## Pay Tuition

- Payments are simulated; no card processing. Each successful call returns `201` with `status: SUCCESS`.
- `paidAmount` in the response is the amount of this payment; `remainingBalance` is the term balance after it.
- `transactionId` (1-64 chars, `A-Z a-z 0-9 _ -`) is generated by the client. A reused ID is rejected with
  `409 DUPLICATE_TRANSACTION`, even if the payload is identical; the original payment is not changed.
- Amount rules: must be `> 0` with at most 2 decimals (`422 VALIDATION_ERROR`), and must not exceed the
  term balance (`422 AMOUNT_EXCEEDS_BALANCE`). Paying a fully paid term is rejected the same way.
- The tuition row is locked (`SELECT ... FOR UPDATE`) during a payment, so concurrent payments cannot
  together exceed the balance.

## Identity and authorization

- Authentication uses JWT bearer tokens issued by `POST /api/v1/auth/login` for seeded demo users.
- Roles: `student`, `bank`, `admin`.
- Token claims: `sub` (username), `role`, `student_no` (students only), `iss`, `iat`, `exp`. Tokens are
  HS256-signed and expire after `JWT_EXPIRE_MINUTES` (default 60). There is no refresh token; the client
  logs in again.
- On every request the user is re-loaded from the database, so a deactivated account loses access
  immediately even with an unexpired token.
- Login returns the same `401 INVALID_CREDENTIALS` for unknown users and wrong passwords, and performs a
  password hash comparison in both cases to avoid revealing valid usernames.
- Errors use one format everywhere: `{"error": {"code": "...", "message": "...", "details": ...}}`.
- Banking endpoints accept the `bank` role (any student) and the `student` role (own student number only).
  The student number is taken from the token subject; a mismatching path/body value returns `403`.

## Mobile query rate limit

- Limited to 3 calls per student number per calendar day, keyed by student number, not client IP.
- The day boundary is computed in the `Europe/Istanbul` time zone.
- Calls for unknown student numbers also count toward the limit (reduces enumeration).
- The limit is enforced both at the gateway and inside the API (database counter, for testability).
- Every call is counted, including rejected ones; the counter is committed before the lookup runs.
- Responses carry `X-RateLimit-Limit` and `X-RateLimit-Remaining`; a `429` also carries `Retry-After`
  (seconds until the next Istanbul midnight).
- Malformed student numbers (`422`) are rejected before counting.

## Query responses

- JSON field names are camelCase (`studentNo`, `tuitionTotal`, `paidAmount`).
- Money values are JSON numbers rounded to 2 decimals.
- A known student with no tuition records returns `200` with zero totals and an empty `terms` list;
  an unknown student returns `404 STUDENT_NOT_FOUND`.
- A student's tuition records are assumed to share one currency; the response reports that currency
  (`USD` when there are no records).

## AI Agent

- The LLM is called through the OpenAI-compatible Chat Completions API with `tool_choice=auto`, so the
  model itself selects tools (no keyword routing). `LLM_PROVIDER=gemini` uses Google's OpenAI-compatible
  endpoint; `LLM_PROVIDER=openai` uses OpenAI. Only `.env` changes between providers.
- Tools: `search_tuition_policies` (MCP), `get_my_tuition` and `pay_tuition` (REST via the gateway).
- No tool takes a student number. The agent always uses the student number of the logged-in user
  (JWT), so a number typed in a prompt cannot be used to read or pay for another student.
- The agent, not the LLM, generates the payment `transactionId` (UUID).
- Default Gemini model is `gemini-3.5-flash-lite`: in November 2026 the `gemini-2.x` models returned
  `404` on the OpenAI-compatible endpoint for this key and `gemini-3.5-flash` was often overloaded
  (`503`). Gemini 3 requires the `thought_signature` of each tool call to be sent back, so the agent
  replays tool calls unchanged.
- If the LLM provider fails in the middle of a question, the question is removed from the chat
  history, and any payment that already succeeded is still reported to the user so it is not repeated.

## API Gateway

- Kong (DB-less, declarative config) is used as the gateway, locally and in the cloud, so the same
  configuration is used everywhere. Azure API Management Consumption tier was not chosen because it does
  not support `rate-limit-by-key`, which is needed for the per-student limit.
